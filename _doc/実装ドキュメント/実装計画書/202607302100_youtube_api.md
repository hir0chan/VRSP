## 1. 背景・目的

ユーザーの意向: 本番公開前に「ほぼ本番同様」の動作確認をローカルで行いたい。そのため MVP で先送りした YouTube Data API v3 連携を実装し、実在配信者の実データを `npm run update` で取得できるようにする。

前提:
- API キーはユーザーが取得中(ローカルは `.env` の `YOUTUBE_API_KEY`、`.env.example` 作成済み)
- 実在配信者リストはユーザーから提供予定(**未着**。着き次第 streamers.yaml を差し替える)
- MVP 計画書(`202607301624_mvp_prototype.md`)で確定済みの方針を引き継ぐ: 配信者単位の失敗は前回データ引き継ぎ、全滅時は書き込まず非0終了、ファイル単位の原子的書込

## 3. 確定仕様

(§2 系はテンプレート上の提案型専用セクションのため省略)

| 項目 | 決定内容 |
|---|---|
| モード切替 | `YOUTUBE_API_KEY` が**設定されていれば実 API、未設定ならモック**(モック使用時は console にその旨を明示出力)。MVP 時の「スタブが空配列を返す事故」は実装が入ることで解消 |
| .env 読込 | `.env` が存在すれば読み込む**最小ローダーを自作**(`KEY=VALUE` 形式のみ、コメント・空行スキップ。既存の環境変数を上書きしない)。**モジュールトップレベルの副作用にせず、CLI 入口(`isCommandLineEntry` 分岐内)から明示的に呼ぶ**(テストで import しても実環境の .env が混入しない)。空文字・空白のみのキーは「未設定」扱い。dotenv 等の依存追加はしない。CI では GitHub Secrets の env 注入をそのまま使用 |
| 取得方式(クォータ節約) | search.list(100 unit)は使わない。①`channels.list`(id を最大50件バッチ, **part=snippet,contentDetails**。snippet はチャンネル名の検証・ログ用でコストは同じ 1 unit)→ uploads プレイリスト ID②チャンネルごとに `playlistItems.list`(maxResults=10, part=contentDetails)→ 直近動画 ID(各1 unit)③`videos.list`(ID を最大50件バッチ, part=snippet,liveStreamingDetails)→ 状態判定(1 unit/50件)。5チャンネルなら1回の更新で **約7 unit**(無料枠 10,000/日に対し15分毎実行でも余裕) |
| Stream への変換 | `liveStreamingDetails` を持つ動画のみ対象(通常動画は除外)。状態判定: `actualEndTime` あり → `ended` / `actualStartTime` あり → `live` / それ以外 → `upcoming`。マッピング: `scheduledStart=scheduledStartTime` / `actualStart=actualStartTime` / `actualEnd=actualEndTime` / `viewers=concurrentViewers`(live のみ。`Number()` 変換後に**有限かつ非負でなければ viewers 自体を省略**)。**upcoming なのに `scheduledStartTime` が無い・いずれかの日時文字列が不正(Date 変換で NaN)な動画は console.warn して除外**。サムネは `snippet.thumbnails`(high → medium → default の順でフォールバック、いずれも無ければ除外して warn)、URL は `https://www.youtube.com/watch?v=<id>` |
| 表示対象の絞り込み | ended は `actualEnd >= now - 24h`(**境界含む**)のみ generated に残す(表示は従来どおり MVP では ended 非表示)。upcoming は `now - 7日 <= scheduledStart <= now + 30日`(**両端含む**)のみ(放置された古い予定枠の混入防止)。live は常に残す。境界は固定 `now` を渡す単体テストで検証 |
| 失敗の定義と成功0件の区別 | fetchStreams の戻り値は配信者ごとの **Result 型**(下記 §3「公開 IF」)で成功/失敗を明示する。以下は**配信者単位の失敗**として扱う: ①`channels.list` のレスポンスに該当 channel item が無い(存在しない ID は HTTP 200 で items から欠けるだけのため、**リクエストした全 ID と items を突き合わせて検出**)②`contentDetails.relatedPlaylists.uploads` が無い ③`playlistItems.list` の HTTP エラー/タイムアウト ④`videos.list` バッチの失敗(**そのバッチに動画を含む全配信者を失敗扱い**)⑤**`channels.list` バッチ自体の失敗**(HTTP エラー・タイムアウト・不正 JSON・レスポンス構造不正): **そのバッチで要求した全配信者を失敗扱いにし、後続バッチは継続**。各エンドポイント共通で、不正 JSON・構造不正はそのリクエストに属する配信者へ帰属させる。一方、`videos.list` が HTTP 200 で**個別の動画 ID を items から欠落**させた場合(削除・非公開化等)は、**欠落動画のみ warn して除外し、配信者は失敗にしない**(要求 ID と items の突き合わせで検出)。「正常に取得して対象配信0件」は**成功(空配列)**であり失敗ではない |
| 失敗時挙動(MVP 計画の方針を実装) | 失敗した配信者は**前回 streams.json の当該配信者分を引き継ぎ**、console.error に記録して続行。全配信者失敗時は書き込まず非0終了。前回ファイルが無い/壊れている場合は引き継ぎなしで続行(warn)。**enabled な配信者が0件の場合は設定エラーとして書き込まず非0終了**。streamers.yaml 内の `youtubeChannelId` 重複も設定エラー(既存の id 重複チェックと同様に非0終了) |
| HTTP | Node 組み込み `fetch` を使用(依存追加なし)。タイムアウト 15秒(AbortSignal.timeout)。API エラー(4xx/5xx)はレスポンス本文の要点を含めて throw |
| streamers.yaml | ユーザー提供の実在チャンネルに差し替える。登録前に `channels.list` で **channelId の実在と名称を検証**してから enabled: true にする(検証は実装後の検証フェーズで実施)。ユーザー提供が実装完了までに間に合わない場合は、実装検証用に Claude が選定した実在チャンネル(2〜3件)で一時確認し、リスト確定後に差し替える |
| youtube.ts の公開 IF | `fetchStreams(streamers: Streamer[], apiKey: string, fetchFn?: typeof fetch): Promise<Map<string, FetchResult>>`、`type FetchResult = { ok: true; streams: Stream[] } \| { ok: false; error: Error }`。成功0件(`ok: true, streams: []`)と失敗(`ok: false`)を型で区別する。fetchFn 注入によりテストではモック fetch で検証(実 API を叩くテストは作らない) |
| テスト | youtube.ts の変換ロジック(状態判定・絞り込み・バッチ分割)と update.ts のマージ/引き継ぎロジックを node:test で追加。既存14テストは不変のまま全パスを維持 |
| スコープ外 | CI ワークフローの変更(cron 有効化・secret 参照)は**本計画に含めない**。本番公開の意思決定後に別途実施(リポジトリ作成自体が未承認のため) |

## 4. 実装設計

### 4.1 新規・変更ファイル

```
scripts/
├── youtube.ts   # 新規: YouTube Data API クライアント + Stream 変換(純関数部は分離)
├── update.ts    # 変更: .env ローダー / モード選択 / 前回データ引き継ぎマージ
├── mock.ts      # 不変
└── models.ts    # 不変(必要なら YouTube API レスポンスの内部型を youtube.ts 内に閉じる)
test/
└── youtube.test.ts  # 新規: 変換・絞り込み・バッチ・マージの単体テスト(fetch モック)
```

- `any` 禁止のため API レスポンスは最小限の型を youtube.ts 内に定義し、実行時は必要フィールドの存在チェック(型ガード)を行う
- update.ts のフロー: streamers 読込 → キー有無でモード決定 → 取得(Map)→ 失敗配信者は前回分を引き継ぎ → 絞り込み → 書込(既存の原子的書込を流用)

### 4.2 変更しないもの

- src/(表示層)・data/generated のスキーマ・既存テスト・.github/workflows・streamers.yaml の書式

## 5. 検証計画

1. **単体テスト**(固定 `now`・モック fetch で決定的に): 状態判定(upcoming/live/ended)・絞り込み境界(24h/過去7日/未来30日の包含)・50件バッチ分割・viewers 不正値の省略・日時欠落/不正動画の除外。**API 異常系**: channels.list レスポンスの item 欠落(=存在しない ID)・uploads 欠落・**channels.list バッチ失敗時に当該バッチの全配信者が失敗し後続バッチは継続すること**・playlistItems の 4xx/5xx・videos.list バッチ失敗時の影響配信者特定・**videos.list の個別動画 ID 欠落(200)は動画のみ除外され配信者は成功のままであること**・タイムアウト(AbortError)・不正 JSON/必須フィールド欠落・成功0件と失敗の区別。**マージ**: 部分失敗時に成功者は更新され失敗者のみ引き継がれる・前回 JSON なし/破損時の挙動・全失敗時に両 generated が完全に不変・enabled 0件で非0終了。`npm test` 全パス(既存14 + 新規)
2. **型・ビルド**: `npm run check` 0 errors / `npm run build` 成功
3. **実データ確認(API キー到着後)**: `.env` 設定 → 検証済み実在チャンネルで `npm run update` → generated に実データが入ること(live が無い時間帯は upcoming のみでも可)→ `npm run dev` でブラウザ確認(実タイトル・実サムネ表示。サムネは外部 URL になるため img の表示確認)
4. **異常系(実環境)**: 不正な API キーで update → 非0終了し既存 generated 不変。streamers.yaml に存在しない channelId を1件混ぜて update → 該当者が**失敗扱い**(前回分引き継ぎ)になり他は正常取得されること(「正常0件」と誤認して空で上書きしないこと)
5. **クォータ実測**: 1回の update の消費 unit を計算値と突き合わせ(Google Cloud Console のクォータ画面で目視確認)
6. **リリース判定条件**: 実在配信者の**予約枠(upcoming)が uploads 経由で取得できること**を実データで確認する(取れない事例が続く場合は取得方式を再検討)

## 6. 影響範囲・リスク

- uploads プレイリスト経由の取得は、チャンネルによって「予約枠が uploads に現れるまでラグがある」事例が知られる。search.list(100 unit)を使わない設計上のトレードオフとして許容し、実データ確認で問題があれば再検討する
- サムネイルが外部(i.ytimg.com)参照になる。表示は問題ないが、モック時代のローカル SVG とは挙動が変わる(オフラインでは表示されない)
- `viewers` は live 中のみ提供され、取得タイミングにより欠落しうる(表示側は既に optional 対応済み)
- API キーの誤コミット対策は .gitignore(`.env`)で担保済み。update.ts はキーの値をログに出さない
