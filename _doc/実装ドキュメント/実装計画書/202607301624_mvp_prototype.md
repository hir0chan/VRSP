## 1. 背景・目的

README.md(開発指示書)に基づき「VRChat系 YouTube 配信者向けホロジュール」を構築する。README はドラフトであり、ユーザーとの対話で以下の進行方針が確定した。

- **モックデータ先行**でプロトタイプを構築し、実際に使いながらブラッシュアップする。YouTube Data API 連携は API キー取得後の後続フェーズとする
- このディレクトリ(VRSP)を git init し、GitHub 新規リポジトリ + GitHub Pages で公開する
- 配信者リストは当初「Claude が仮選定した実在配信者を登録」で合意したが、実在配信者名で架空のモック配信予定を公開ページに表示するリスクを避けるため、**MVP は架空配信者とし、実在リストは API 連携フェーズで channelId 検証とセットで登録**する方針に変更(実装レポートでユーザーに報告する)
- 細部仕様は Claude が割り切って決定し、実装レポートに「決めた仕様」として明記する

本計画書は最初の MVP プロトタイプ(画面 + データ生成パイプライン + デプロイ)を対象とする。

## 3. 確定仕様

| 項目 | 決定内容 |
|---|---|
| フレームワーク | Astro(静的出力)+ TypeScript strict。`any` 禁止 |
| データフロー | `scripts/update.ts` → `data/generated/streams.json` / `streamers.json` → Astro build がビルド時に import |
| MVP のデータ生成 | **モック固定**。update.ts に API 分岐を置かない。`youtube.ts`(実 API クライアント)は API 連携フェーズで新設し、切替もその時点で実装する(未実装スタブによる空データ上書き事故を構造的に排除) |
| モックデータ内容 | live 2件 / 本日 upcoming 3件 / 翌日以降 upcoming 4件 / ended 2件。`generateMockStreams(streamers, now)` は基準時刻を引数に取る純関数とし、update.ts が実行時刻を渡す。件数・シナリオも引数で制御(本番コードに検証用 env 分岐を作らない) |
| streamers.yaml(MVP) | **架空の配信者 5名**(`enabled: true`)。実在配信者の名前で架空の配信予定を公開ページに表示することを避けるため。実在配信者リストは API 連携フェーズで channelId 検証とセットで登録する |
| streamers.yaml 検証 | id 重複・必須フィールド欠落・型不正は**設定ミスとして update を非0終了**(generated は書き換えない)。設定ファイル起因のエラーは静かにスキップしない |
| データモデル | README §7 の `Streamer` / `Stream` に完全準拠。`Status = "upcoming" \| "live" \| "ended"` |
| generated スキーマ | streams.json: `{ updatedAt: string(ISO), streams: Stream[] }` / streamers.json: `{ updatedAt: string(ISO), streamers: Streamer[] }`。`updatedAt` は**最後に update が正常完了した時刻**(フッターに「最終更新」として表示) |
| 取得失敗時の挙動(API フェーズ適用) | 配信者単位で失敗を記録して続行(README §13)。失敗した配信者は**前回 generated の当該配信者データを引き継いで**マージ書込。全配信者失敗時は書き込まず非0終了 |
| 書込方式 | **ファイル単位で原子的**(一時ファイル→rename)。両 JSON の生成・検証完了後にまとめて rename する。2ファイル間の完全な原子性は保証しない(不整合窓は許容。次回更新で解消) |
| render.ts | **作らない**。README §4 に記載はあるが Astro がレンダリングを担うため役割が重複。JSON 書出は update.ts 内の小関数に分離 |
| 画面構成 | トップページのみ。NOW ON LIVE(大カード)→ TODAY(開始時刻順)→ UPCOMING(日付ごとグループ)。live 0件時は NOW ON LIVE セクション非表示 |
| セクション分類 | JST(Asia/Tokyo)固定。TODAY = 当日 00:00〜23:59 に `scheduledStart` がある upcoming(live とは重複させない)。`scheduledStart` 欠落の upcoming は UPCOMING 末尾「日付未定」グループ。live の `actualStart` 欠落は時刻表示なしでカード表示。ended は MVP では非表示(generated には含める) |
| streamerId 結合 | `src/lib/classify.ts` の純関数として実装(streamers.json から Map を構築し streams と結合)。未知の `streamerId` はビルド時 warn してその配信をスキップ。index.astro は結合済み結果を表示するだけ(結合ロジックを単体テスト可能に保つ) |
| UI | 日本語、ダークテーマ、アクセント赤のみ、レスポンシブ。プレーン CSS(`src/styles/global.css`)。CSS フレームワーク不使用。サムネイルはリポジトリ内 SVG プレースホルダ(外部サービス非依存) |
| 依存パッケージ | devDependencies: `astro`, `typescript`, `tsx`, `yaml`, `@astrojs/check`, `@types/node` のみ。CI 含めすべて package.json scripts 経由で実行(暗黙の npx ダウンロード禁止) |
| テスト | `node:test` を `tsx --test` で実行(`npm test`)。追加テストフレームワーク不採用 |
| デプロイ | GitHub リポジトリ名 `VRSP`(ユーザーアカウント配下)。GitHub Pages(公式 actions/configure-pages → upload-pages-artifact → deploy-pages)。Astro `base: '/VRSP/'`、`site` はリポジトリ作成後に確定 |
| Actions トリガー別ステップ | **push(main)**: install → test/check → build → deploy(update は実行しない。コミット済み generated を使用)/ **workflow_dispatch**: update → generated に差分があればコミット&push(コミットメッセージに `[skip ci]` を付け、push トリガーの二重 build/deploy を防止)→ build → deploy / **schedule(15分毎)**: dispatch と同一ステップだが、**モック期間中は cron をコメントアウト**(API 連携フェーズで有効化) |
| Actions 権限・排他 | update ジョブ: `contents: write` + github-actions[bot] の commit identity。deploy: `pages: write`, `id-token: write`。`concurrency: group: pages-deploy, cancel-in-progress: false` で push/schedule の同時実行による競合・古い成果物での上書きリスクを低減(全実行の順序保証まではしない) |
| generated の git 管理 | コミットする(README §13「既存 generated を残す」を CI 上で成立させる最も単純な方法)。schedule コミットによる履歴汚染は許容(将来課題) |

### 成立性の根拠(調査済み)

- リポジトリは現在 README.md と _doc のみで既存コードなし(2026-07-30 に `ls` で確認)。競合・回帰の対象が存在しない
- Astro の静的出力 + ビルド時 JSON import は標準機能であり、サーバ常駐・DB 不要の要件を満たす
- モック生成を純関数(基準時刻・件数を引数)にすることで、決定的なテストと実行時利用を同一コードで両立できる

## 4. 実装設計

### 4.1 データ層(scripts/)

```
scripts/
├── models.ts    # Streamer / Stream / Status 型定義(README §7 準拠)+ generated スキーマ型
├── mock.ts      # generateMockStreams(streamers: Streamer[], now: Date, opts?): Stream[]
```

## 5. 検証計画

1. **正常系**: `npm run update` → generated 2ファイル生成、`npm run build` 成功、`npm run dev` でブラウザ確認(chrome-devtools MCP でスクリーンショット): 3セクション表示・視聴ボタン・レスポンシブ(375px / 1280px)
2. **異常系(README §13 の核心)**:
   - streamers.yaml を故意に壊す(id 重複・フィールド欠落)→ update が非0終了し、**既存 generated が内容不変**であること
   - 書込途中の失敗を模したテスト(rename 前に例外)で既存ファイルが壊れないこと(単体テスト)
3. **境界(classify.ts 単体テスト)**: JST 00:00 直前/直後・日付跨ぎ(23:50 開始)・月末年末・`scheduledStart` 欠落 upcoming(日付未定グループ)・`actualStart` 欠落 live・streamerId 結合関数での未知 ID スキップ(warn 出力含む)
4. **モック生成テスト**: 固定 `now` を渡して決定的出力を検証。live 0件シナリオ(opts 指定)→ classify 結果で NOW ON LIVE 空、画面上はセクション非表示(dev サーバで目視確認)
5. **型・規約**: `npm run check`(astro check + tsc --noEmit)がエラー0(strict, any 禁止)
6. **デプロイ**: GitHub リポジトリ作成 → push → Actions 成功 → Pages URL で表示確認(base パス配下でアセット・リンク切れなし)→ workflow_dispatch 実行で generated 更新コミット + 再デプロイを確認

## 6. 影響範囲・リスク

- 新規構築のため既存への影響なし
- GitHub Actions の schedule は厳密な15分間隔を保証しない(混雑時遅延)。README の要件は「15分ごとに起動を試みる」と解釈し、遅延は許容する
- モック期間中は cron 無効のため「15分毎更新」は未検証のまま API フェーズへ持ち越し(workflow_dispatch で同一パスを検証することで代替)
- generated コミット方式は履歴を汚すトレードオフあり(将来課題: orphan ブランチ化等。MVP では単純さ優先)
- 2つの generated JSON 間の不整合窓(書込途中クラッシュ)は理論上残るが、次回 update で解消されるため許容

## 7. 未決事項(デフォルト採用・変更可)
