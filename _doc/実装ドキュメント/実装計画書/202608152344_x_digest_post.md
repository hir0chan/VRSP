## 1. 背景・目的

新たに live になった配信を X(旧 Twitter)で告知したいというユーザー要望。個別ポストは実測で日本語のみでも約111件/日(git 履歴 8/8〜8/11 の4日実測: 97〜127件/日)となり X 無料枠・IFTTT の投稿制限を超えるため、**2時間毎のダイジェスト投稿**方式で合意した。投稿経路は IFTTT Webhooks(ユーザーは IFTTT 課金ユーザー。X Developer 登録・OAuth 実装が不要になり、X 側の投稿枠は IFTTT のパートナー枠を使う)。

ユーザー合意済み事項(2026-08-15):

| 論点 | 合意 |
|---|---|
| 方式 | ダイジェスト(個別ポストしない) |
| 経路 | IFTTT Webhooks(GitHub Actions → IFTTT → X) |
| 頻度 | 2時間に1回まで(投稿判定は120分以上経過。下記) |
| 対象 | 日本語配信のみ・全プラットフォーム(YouTube / Twitch / ニコ生) |
| 文面 | 配信者名を列挙+残り件数+現在の live 総数+サイト URL |
| 0件時 | 投稿スキップ |
| 時間帯 | 24時間投稿(深夜帯もスキップしない) |
| アカウント | 当面ユーザーの個人 X アカウント(将来専用アカウントへ。IFTTT 側の接続切替のみで対応でき、コード変更不要) |

## 3. 確定仕様

| 項目 | 決定内容 |
|---|---|
| 実行形態 | 新規 `scripts/digest.ts` を CI の「Update generated data」成功後・「Commit generated data」前の独立ステップで実行。`update.ts` の取得・書込ロジックには一切手を入れない(型ガード等の export 追加のみ) |
| 入力 | `data/generated/streams.json`(update 直後のもの)と `data/generated/streamers.json`(配信者名の解決) |
| 「新規 live」の定義 | `status === "live"` かつ `isJapanese === true`(undefined は対象外)かつ**投稿済み集合に含まれない**もの。投稿時点で live 中であることが条件(窓内に開始して既に終了した配信は載せない。視聴導線にならないため) |
| 投稿済みキー | `${platform ?? "youtube"}:${stream.id}` の複合キー(stream.id の一意性は各プラットフォーム内でしか保証されないため) |
| 状態ファイル | `data/generated/digest.json` **新規**。`{ lastPostedAt?: string, announced: { id: string, at: string }[] }`(id は上記複合キー)。一時ファイル→rename の原子的書込(discovery.json と同パターンのヘルパーを digest.ts 内に複製。update.ts の `writeAtomic` は型が限定されており、汎用化はしない) |
| announced の剪定 | 書込のたびに「現在 live でなく、かつ `at` が24時間より古い」エントリを除去(live 継続中は年齢によらず保持=長時間配信の再告知防止。Twitch/ニコ生の一時的取得失敗による消失→復帰はこの24時間保持で再告知を防ぐ) |
| 初回の扱い | **digest.json が ENOENT の場合のみ**、現在の live 全件を announced に記録して投稿しない(ベースライン)。JSON 破損・型不正は**非0終了・state 無変更**(初回扱いにしない。黙って通知を失わない) |
| state の妥当性検証 | `announced[].id` は空でない文字列、`announced[].at` はパース可能な日時、キーの重複は禁止。いずれかに違反したら state 全体を拒否して非0終了・無変更(不正な `at` が NaN 比較で永久に剪定されない事態を防ぐ) |
| lastPostedAt の異常値 | パース不能は非0終了。未来値は now+24時間以内なら「now とみなして」スキップ(時計ずれ吸収・影響は最大でも約1日で解消)、それを超える未来値は非0終了(手動復旧) |
| 投稿条件 | `now - lastPostedAt >= 120分` かつ新規 live が1件以上(「2時間に1回まで」の上限保証。cron 遅延は間隔を延ばす方向にしか働かないため安全値の減算はしない。最大12件/日=月360件が確定) |
| 投稿保証の意味論 | **Webhook 送信は再試行優先=応答喪失時の重複を許容**。POST 成功後の state 書込失敗・commit/push 失敗・IFTTT 受理後の応答喪失では次回同内容を再投稿しうる(IFTTT/X に冪等キーがなく完全防止は不可能。ダイジェストの重複は低害と判断)。投稿失敗時は state 無変更で次回自動リトライ。**X 投稿までの at-least-once 配送は保証しない**(IFTTT 受付後の X アクション失敗は再送されない) |
| lastPostedAt の意味 | 「IFTTT が Webhook を**受け付けた**時刻」。IFTTT→X の非同期投稿の成否までは確認できない(投稿保証なし。失敗は IFTTT のアクティビティ画面で確認する運用) |
| 投稿手段 | `POST https://maker.ifttt.com/trigger/vrsp_digest/with/key/${IFTTT_WEBHOOK_KEY}`、JSON `{ "value1": <本文全文> }`、`redirect: "error"`。タイムアウト15秒。非 2xx・fetch 失敗はその回の投稿を断念(state 無変更→次回リトライ) |
| キー漏洩対策 | キーは環境変数からのみ読む(CLI 引数・state・本文に入れない)。エラーメッセージ・ログに URL(キー含む)・レスポンス本文・`Response.url` を一切出さない(ステータスコードのみ可) |
| 文面 | 下記テンプレート。X の重み付き文字数(CJK=2・URL=23、上限280)以内に名前列挙を自動切り詰め |
| 文字数計算 | twitter-text の簡易版を自前実装: 末尾のサイト URL は23固定、Latin-1 等の軽量範囲は1、その他(CJK・絵文字含む)は2として計算(判定不能は2の安全側)。依存追加はしない |
| 配信者名のサニタイズ | 外部入力(第三者が制御可能)のため投稿前に正規化: ①制御文字・改行→空白、連続空白の縮約 ②メンション・タグ・リンク化の開始文字をすべて中黒(U+30FB `・`)へ置換: アットマーク(U+0040 `@`・U+FF20 `＠`。**twitter-text は全角も開始記号と認識するため両方**)、ハッシュ(U+0023 `#`・U+FF03 `＃`。同上)、ドット類(U+002E `.`、U+FF0E `．`、U+3002 `。`、U+FF61 `｡`。URL 自動リンク化=23文字扱いを防止。全角ピリオド温存は URL 正規化で ASCII に戻される実装があるため不可) ③1名あたり重み付き長40(全角20文字相当)で切り詰め+「…」。サニタイズ後が空になる名前はその配信を列挙から外し件数のみに含める |
| モック誤投稿ガード | digest.ts は `IFTTT_WEBHOOK_KEY` と `YOUTUBE_API_KEY` の**両方**を独立に検査し、どちらかが未設定/空なら「スキップします」ログのみで正常終了・state 無変更(CI で YOUTUBE_API_KEY が欠落すると update がモックデータを生成して成功終了するため、update の成功だけでは本番データの保証にならない) |
| 失敗時の CI への影響 | digest ステップは `continue-on-error: true`。投稿失敗はビルド・デプロイを止めない(スクリプトは非0終了で失敗を可視化) |
| コミットステップ修正 | 既存の `git diff --quiet -- data/generated` は**未追跡ファイルを検出しない**ため、初回の digest.json だけが差分の実行でコミットされない。`git add data/generated` → `git diff --cached --quiet -- data/generated` 方式に変更する(既存挙動と等価+未追跡対応) |
| Secrets | `IFTTT_WEBHOOK_KEY` を新設(ユーザーが登録)。イベント名 `vrsp_digest` はコード内定数(秘密ではない)。漏洩時は IFTTT 側でキー再生成→ Secrets 更新(運用手順としてレポートに記載) |
| --dry-run | `npm run digest -- --dry-run` で本文を標準出力に表示し、投稿も state 書込もしない(検証用。キー未設定でも動作)。main の処理順: 引数検証(未知の引数は非0終了)→ dry-run なら入力読込+本文表示して終了 → 非 dry-run のみ両キー検査(欠落は正常終了スキップ)→ 入力読込 → 投稿判定 → POST → state 書込 |

### 文面テンプレート

```
🔴 VRChat配信が新たにスタート!
{名前1} / {名前2} / {名前3} ほか{N}件
現在{M}件がライブ配信中👀
https://hir0chan.github.io/VRSP/
```

- 名前は streamers.json から解決し、上記仕様でサニタイズ。解決できない streamerId の配信は列挙から外し件数には含める
- 2行目: 文字数上限内に収まるだけ名前を列挙し、残りがあれば「ほか{N}件」。全員載るなら「ほか」句は省略。名前が1件も載らない場合は「{N}件の配信がスタート!」形式に退避
- {M} = 現在 live 中の日本語配信の総数(全プラットフォーム)
- 並び順は決定的に: 有効な `actualStart` の昇順(先に始まった順)→ 欠落・パース不能は末尾 → 同値は複合キーの辞書順

### 成立性の根拠(調査済み)

- git 履歴実測(8/8〜8/11)で新規 JP live は約111件/日。2hダイジェストは最大12件/日=月360件で、IFTTT の既知のどの制限水準(25〜200件/日)にも収まる
- `streams.json` の全プラットフォーム streams に `isJapanese` が付与されていることを現データで確認(YouTube 含む)。announced 複合キーの一意性は platform 接頭辞で担保
- CI の cron 定義は `3,18,33,48 * * * *`(15分間隔。ただし実測ではGitHub 側の間引きにより約30分間隔で実行されている)。投稿判定は実行回数でなく経過時間ベースなので cron 頻度の変動に影響されない
- update が本体ファイルを書かない経路(追跡0件+クールダウン+プラットフォーム全滅)でも digest.json 単独の差分が発生しうることを update.ts:457-462 で確認 → コミットステップ修正で対応

## 4. 実装設計

### 4.1 スクリプト

- `scripts/digest.ts` **新規**。純関数と副作用を分離:
  - `announcedKey(stream: Stream): string` — 複合キー生成
  - `selectNewLives(streams: Stream[], announced: AnnouncedEntry[]): Stream[]` — 新規 JP live の抽出+決定的ソート
  - `countLiveJapanese(streams: Stream[]): number`
  - `sanitizeName(name: string): string` — 上記サニタイズ仕様
  - `weightedLength(text: string): number` — 簡易 twitter-text 実装
  - `composeDigest(newLives: Stream[], liveTotal: number, streamers: Streamer[]): string` — テンプレート適用+切り詰め
  - `shouldPost(state: DigestState, now: Date): boolean` — 120分判定+未来値規則
  - `pruneAnnounced(announced: AnnouncedEntry[], liveKeys: Set<string>, now: Date): AnnouncedEntry[]`
  - `postToIfttt(text: string, key: string, fetchFn?: typeof fetch): Promise<void>` — 失敗時 throw(メッセージにキー・URL・レスポンス本文を含めない)
  - state の読込は ENOENT のみ初回扱い、破損・型不正・重複キー・不正日時は throw。書込は digest.ts 内の原子的書込ヘルパー(update.ts と同パターンの複製)
  - main: 引数検証 → dry-run 分岐 → 両キー検査 → streams/streamers 読込(update.ts の `isStream` / `isStreamer` を export して再利用)→ 初回ベースライン or 投稿判定 → 投稿 → state 書込(順序の詳細は §3「--dry-run」)
- `scripts/models.ts`: `DigestState` / `AnnouncedEntry` を追加
- `package.json`: script `"digest": "tsx scripts/digest.ts"` 追加

### 4.2 CI(update.yml)

「Update generated data」と「Commit generated data」の間に追加:

```yaml
      - name: Post digest to X
        if: github.event_name != 'push' && steps.update.outcome == 'success'
        continue-on-error: true
        env:
          IFTTT_WEBHOOK_KEY: ${{ secrets.IFTTT_WEBHOOK_KEY }}
          YOUTUBE_API_KEY: ${{ secrets.YOUTUBE_API_KEY }}
        run: npm run digest
```

「Commit generated data」の diff 判定を未追跡ファイル対応に変更:

```sh
git add data/generated
if git diff --cached --quiet -- data/generated; then
  exit 0
fi
git config user.name "github-actions[bot]"

```

### 4.3 ユーザー側の手動セットアップ(実装レポートに手順を記載)

1. IFTTT でアプレット作成: If「Webhooks - Receive a web request」(イベント名 `vrsp_digest`)→ Then「X - Post a tweet」(本文 = `{{Value1}}` のみ)
2. IFTTT の Webhook キーを GitHub リポジトリ Secrets `IFTTT_WEBHOOK_KEY` に登録
3. 運用: X 投稿の成否は IFTTT のアクティビティ画面で確認(Webhook 受付成功≠X 投稿成功)。キー漏洩時は IFTTT でキー再生成→ Secrets 更新

### 4.4 変更しないもの

- `update.ts` の取得・分岐・書込ロジック(isStream/isStreamer の export 化のみ。writeAtomic は変更せず digest 側に複製)
- streams.json / streamers.json / discovery.json のスキーマ
- 表示層(src/)全体
- 既存テスト

## 5. 検証計画

1. **正常系**: `npm test`(新規 `test/digest.test.ts` 含む全パス)・`npm run check` 0 errors・`npm run build` 成功。fetchFn モックで: 新規2件+既知1件 → 本文に新規2件のみ列挙・announced 追記(複合キー)・lastPostedAt 更新
2. **異常系**:
   - IFTTT 非2xx / fetch 失敗 / タイムアウト → 非0終了・state 無変更。標準出力・標準エラーに生キー・URL エンコード済みキー・URL 全体・レスポンス本文が現れないこと
   - streams.json / digest.json の JSON 破損・型不正・announced の重複キー・`at` の不正日時 → 非0終了・state 無変更(初回扱いにならないこと)
   - `IFTTT_WEBHOOK_KEY` 未設定 / `YOUTUBE_API_KEY` 未設定(それぞれ単独)→ 正常終了・無投稿・state 無変更
   - 未知の CLI 引数 → 非0終了
   - POST 成功後の state 書込失敗を注入 → 非0終了・旧 state 維持(=次回再投稿対象になる。仕様どおりの重複許容)
   - state 書込後の commit/push 失敗は設計確認項目とする: state はローカルにのみ更新され、次回はリポジトリ上の旧 state から再投稿される(重複許容の範囲内)
3. **境界**:
   - 経過 119分59秒 → スキップ、120分ちょうど → 投稿。lastPostedAt 未来値(+1h)→ スキップ、(+25h)→ 非0終了
   - 新規0件 → スキップ。初回(ENOENT)→ ベースライン記録のみ・無投稿
   - 名前多数で上限超過 → 切り詰め+「ほか{N}件」、重み付き長が280以下。名前0件 → 件数形式へ退避
   - 悪意ある配信者名: 改行・制御文字・`@user`・`＠user`(全角)・`#tag`・`＃tag`(全角)・URL(`t.co/xxx` 等)・絵文字・結合文字 → サニタイズ後の本文が壊れず、リンク化・メンション・タグの開始文字(`@` `＠` `#` `＃` およびドット類)が一切残らないこと
   - announced 剪定(24h 超過+非 live のみ除去、live 継続は保持)。異なるプラットフォームの同一生 ID が別キーになること
   - `actualStart` 欠落・不正・同値のソートが決定的であること
4. **CI 統合**:
   - 未追跡 digest.json のみが差分の場合にコミットされること(修正後のコミットステップをローカルの一時リポジトリで再現確認)
   - update.yml のステップ条件: push → update/digest/commit 全スキップ、schedule / workflow_dispatch → 実行、update 失敗(outcome=failure)→ digest スキップ
5. **実投稿(実環境・ユーザー実施)**: ローカルでの実投稿はしない(チェックアウト時点の古いデータからの投稿と state 汚染を避ける)。手順: ①実装を main へ push(この時点では Secrets 未登録のため digest はスキップされ、初回実行でベースラインがコミットされる…の前にキー検査で止まるため、Secrets 登録後の初回実行でベースラインコミット)②IFTTT アプレット+Secrets 登録 ③次の cron 実行でベースライン記録(無投稿)を確認 ④さらに次以降の実行で実投稿1件と digest.json 差分・IFTTT アクティビティを確認。state の正は常にリポジトリの digest.json
6. **回帰**: 既存テスト全パス。`YOUTUBE_API_KEY=` のモック実行(`npm run update` → `npm run digest`)で digest がスキップされ state が生まれないこと。コミットステップ修正後も「差分なしなら exit 0」の既存挙動が保たれること

## 6. 影響範囲・リスク

- 追加中心(digest.ts / test / models の型追加 / update.yml 1ステップ+コミット判定修正 / package.json 1行)。update.ts は export 追加のみで挙動不変
- **二重投稿は「まれに起こりうる」仕様**(Webhook 送信は再試行優先の意味論。push 競合・応答喪失時)。ダイジェストの重複は低害と判断し、完全防止のための二段階コミット方式は過剰設計として不採用
- **X 投稿の成功保証はない**(IFTTT 受付までしか確認できない)。失敗の検知は IFTTT アクティビティ画面の運用でカバー
- IFTTT の X アクション上限はプラン別数値が非公開(過去に 25〜200件/日水準の変動歴)。12件/日はどの水準にも収まるが、IFTTT 側の仕様変更で投稿が止まるリスクはある(止まっても CI・サイト本体には無影響)
- 個人アカウント運用のため、X 側のスパム判定リスクは低頻度・定型文+URL の範囲で許容。専用アカウント移行時は IFTTT の接続切替のみ
- コミットステップの diff 判定変更は全 data/generated に及ぶが、`git add` 後の `--cached` 判定は従来判定の上位互換(未追跡を拾えるようになるだけ)
