# パイプライン実行履歴の永続化 実装計画書

日付: 2026-06-20
種別: 提案型（合意後に計画型へ移行）
状態: **実装・検証完了**（架空。本書は記入例。実施結果は文末「9. 実施結果」参照）
担当: コーディング codex / レビュー・検証 Claude

## 1. 背景・目的

パイプラインの実行状態は現在 `main.py` のモジュール変数 `_job_state`（dict + Lock）に
メモリ保持されており、**サーバを再起動すると実行履歴がすべて消える**。複数週並列化・
ブラウザ実行と機能が増えた結果、「先週どの週をいつ流したか」「過去の失敗週とその
エラー内容」を後から参照したいという運用ニーズが生じている。

本改修では実行履歴を DB に永続化し、ブラウザの新「実行履歴」画面と API から過去の
バッチ実行（対象週・成否・所要時間・エラー）を参照できるようにする。これにより
再起動をまたいだ追跡と、障害時の原因切り分けを可能にする。

---

## 2-1. 技術的可否

**結論: ⭕ 可能。** 前提改修は不要（既存の DB 接続とジョブ機構をそのまま使える）。

### 可否判断の根拠（調査結果）
1. 実行状態は `main.py` の `_run_pipeline_job` / `_run_weeks_parallel` の一箇所で更新され、
   完了結果は `result = {"week_num","status","message","elapsed_sec"}` の統一 dict に
   集約されていることをコードで確認。**この dict を DB へ書く 1 フックを足すだけ**で履歴化できる。
2. マイグレーションは `migration_service.migrate()` が `resource/migration/V1_XX__*.sql` を
   起動時に流す仕組み（Flyway 命名）。履歴テーブルは新規 SQL 1 本の追加で作れる。
3. DB 接続は `src/utils/db.py: get_connection()` に一元化済み。履歴書き込みもこれを流用できる。
4. **ただし重要な制約**: パイプラインの全テーブルは実行ごとに DROP&CREATE される
   （`migrate()` が毎回全 DROP）。履歴テーブルを通常マスタと同じ扱いにすると毎回消える。
   → 履歴は「DROP 対象から除外する専用テーブル」にする必要がある（§3 で確定）。

### 必須の前提改修（あれば）
なし。ただし上記4の「DROP 除外」を migrate 側に実装する必要がある（前提改修ではなく本改修の一部）。

## 2-2. 実現方式の比較

### 案A: 専用DB上の永続テーブルに履歴を書く（推奨）
履歴専用テーブル `pipeline_run_history` を作り、`migrate()` の全 DROP 対象から除外する。

- ⭕ 既存の DB・接続・ジョブ機構をそのまま使え、追加インフラ不要
- ⭕ SQL で集計・検索できる（週別の成功率、平均所要時間など将来拡張に強い）
- ❌ migrate() の「全テーブル DROP」ロジックに除外リストを設ける改修が要る

### 案B: JSON ファイルに追記（resource/csv/output 配下等）
履歴を `history.jsonl` のようなファイルに追記する。

- ⭕ DB を触らない。最も単純
- ❌ 並列実行・複数プロセスからの追記でロック管理が必要。検索性が低い
- ❌ 週並列化（別プロセス）と相性が悪く、競合制御を自前で書くことになる

**結論: 案Aを推奨。** DROP 除外の小改修だけで、DB の検索性と既存機構の流用という利点が得られる。
案Bのファイルロックを自前で持つより、単一 MySQL に集約する方が並列実行とも整合する。

## 2-3. 実装前に確認したい点
1. 履歴の保持期間: 無制限に貯めるか、N 日 / N 件で自動削除するか（**推奨: 当面無制限。
   肥大化したら別途パージ。1実行=数行のため当面問題ない**）
2. 記録粒度: 「バッチ単位（1回の run/run_multi）＋週単位の結果」の2階層でよいか（**推奨: それでよい**）
3. 失敗週のエラーメッセージ全文を保存するか、先頭 N 文字に切るか（**推奨: TEXT 型で全文保存**）

## 3. 確定仕様
| 項目 | 決定内容 |
|---|---|
| 履歴テーブル | 新規 `pipeline_run_history`（バッチ単位）＋ `pipeline_run_week`（週単位、batch_id で親子） |
| DROP 除外 | `migrate()` の全 DROP 対象から上記2テーブルを**除外**（履歴は実行をまたいで永続） |
| 記録タイミング | バッチ開始時に history 行を insert（status=running）、各週完了時に week 行を insert、バッチ完了時に history を update（finished_at・成否集計） |
| 保持期間 | 無制限（自動パージなし。将来必要なら別途） |
| エラー保存 | week 行の `message` を TEXT 型で全文保存 |
| 既存挙動との関係 | `_job_state`（メモリ）は現状どおり残す。履歴 DB は**追記専用の副系**で、進捗ポーリングは従来どおり `_job_state` を見る |
| 並列実行 | 週並列（別プロセス）でも各週完了は親プロセスが集約して書くため、書き込みは親プロセス1点に集約 |

### 成立性の根拠（調査済み）
- 週並列時も結果は親プロセスの `_run_weeks_parallel` が `as_completed` で集約しており、
  **DB 書き込みを親に集約すれば子プロセスからの並行 INSERT は発生しない**（競合なし）。
- history/week への書き込みは1実行あたり数行で、330秒級の処理時間に対し無視できる。

## 4. 実装設計

### 4.1 バックエンド

新規マイグレーション `resource/migration/V1_50__create_pipeline_run_history.sql`:
```sql
CREATE TABLE pipeline_run_history (
  batch_id      BIGINT AUTO_INCREMENT PRIMARY KEY,
  week_nums     VARCHAR(255) NOT NULL,     -- "202514,202515"
  workers       INT NOT NULL DEFAULT 1,
  status        VARCHAR(16) NOT NULL,      -- running | done
  success_count INT, error_count INT,
  started_at    DATETIME NOT NULL,
  finished_at   DATETIME
);
CREATE TABLE pipeline_run_week (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  batch_id   BIGINT NOT NULL,
  week_num   INT NOT NULL,
  status     VARCHAR(16) NOT NULL,         -- success | error
  message    TEXT,
  elapsed_sec DOUBLE,
  INDEX idx_batch (batch_id)
);
```

新規サービス `src/service/run_history/run_history_service.py`:
```python
def begin_batch(week_nums: list[int], workers: int) -> int      # history を insert し batch_id を返す
def record_week(batch_id: int, result: dict) -> None            # week 行を insert
def finish_batch(batch_id: int, results: list[dict]) -> None    # history を done に update
def list_batches(limit: int = 50) -> list[dict]                 # 履歴一覧（週内訳つき）
```

`migration_service.migrate()`: 全 DROP ループに `HISTORY_TABLES = {"pipeline_run_history","pipeline_run_week"}`
の**除外条件**を追加（`if table in HISTORY_TABLES: continue`）。テーブルが無ければ作成、あれば保持。

`main.py`: `_run_pipeline_job` / `run_pipeline_multi` の開始・週完了・終了の3点に
run_history_service のフックを差す（`_job_state` 更新と並べて呼ぶ。例外は握って履歴失敗が
本処理を止めないようにする）。

| エンドポイント | 内容 |
|---|---|
| `GET /pipeline/history?limit=50` | `{"batches": [{batch_id, week_nums, workers, status, success_count, error_count, started_at, finished_at, weeks:[{week_num,status,message,elapsed_sec}]}]}` |

注意: `app.mount("/", StaticFiles...)` より前にルート定義（既存制約）。

### 4.2 フロントエンド
新規ルート `frontend/app/history/page.tsx`（`trailingSlash: true` 設定済みなので `out/history/`
が生成される）。`GET /pipeline/history` を取得し、バッチを新しい順にテーブル表示
（実行日時・対象週・並列数・成功/失敗数）、行展開で週内訳（成否・所要時間・エラー全文）を表示。
共通ヘッダのナビに「実行履歴」を追加。ビルドは `cd frontend && npm run build` で `out/` 再生成。

### 4.3 変更しないもの
- `run_pipeline(week_num)` 本体の計算ロジック・出力CSV構成
- 進捗ポーリングの仕組み（`_job_state` ベースのまま。履歴 DB は参照専用の副系）
- 週並列化の DB 分離方式（`{KASEDB_NAME}_{week}`）。履歴は親プロセスが本体 DB に書く

## 5. 検証計画
1. **正常系（逐次）**: `python main.py 202514` 実行後、`GET /pipeline/history` に
   バッチ1件＋週1件（success・elapsed_sec）が記録されること。
2. **正常系（並列）**: `PIPELINE_WORKERS=2 python main.py 202514 202515` 後、
   history に workers=2 のバッチ1件＋週2件が記録されること（親集約で重複なし）。
3. **永続性**: 上記後に `migrate()` を含む再実行（別週）をしても**過去の履歴行が残る**こと
   （DROP 除外が効いている確認）。
4. **異常系**: 不完全週で1週失敗 → 該当 week 行が status=error・message にエラー全文、
   history の error_count=1 が記録されること。
5. **回帰**: 履歴フック追加後に 202514 をフルラン → ゴールデン比較で全テーブル一致
   （履歴書き込みが計算結果に影響しないこと）。
6. **UI**: `npm run build` 後にブラウザ（chrome-devtools MCP）で履歴一覧・週内訳展開を確認。
7. **後始末**: 検証で作った履歴行と一時週ディレクトリを削除して原状回復。

## 6. 影響範囲・リスク
- 変更は migration 1本・新規サービス・main.py のフック3点・新規フロント1画面。計算ロジックは無変更。
- `migrate()` の DROP 除外は**全機能に影響する箇所**のため、除外テーブル名のタイポに注意
  （誤ると履歴が毎回消える / 誤った除外で別テーブルが残る）。検証3で担保。
- 履歴書き込み失敗（DB一時障害等）が本処理を巻き込まないよう、フックは try/except で隔離する。
- `_job_state` と DB 履歴の二重管理になるが、役割分担（進捗=メモリ / 監査=DB）として許容。
